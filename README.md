rdmo-plugins-gnd
================

This plugin implements dynamic option set, that queries the API for the Gemeinsame Normdatei at https://lobid.org/gnd.
The keyword provider uses [DNB's live SRU service](https://www.dnb.de/sru) for subject headings and multilingual vocabulary mappings.
An optional **local keyword provider** uses a shared SQLite FTS5 index; see the
[Ubuntu installation and index administration guide](docs/local-index.md).

If you intend to use the API, please follow it's [usage policy](http://lobid.org/usage-policy/).


Setup
-----

Install the plugin in your RDMO virtual environment using pip (directly from GitHub):

```bash
pip install git+https://github.com/rdmorganiser/rdmo-plugins-gnd
```

Add the `rdmo_gnd` app to `INSTALLED_APPS` and the plugin to `OPTIONSET_PROVIDERS` in `config/settings/local.py`:

```python
INSTALLED_APPS += ['rdmo_gnd']

...

OPTIONSET_PROVIDERS += [
    ('gnd', _('GND Provider'), 'rdmo_gnd.providers.GNDProvider'),
    ('gnd_keyword_synonyms', _('GND Keyword Synonym Provider'), 'rdmo_gnd.providers.GNDKeywordSynonymProvider'),
    ('gnd_sru_keywords', _('GND SRU Keywords Provider'), 'rdmo_gnd.providers.GNDSRUKeywordsProvider'),
]
```

The option set provider should now be selectable for option sets in your RDMO installation. For a minimal example catalog, see the files in `xml`.

Keyword searches in German and English
-------------------------------------

Choose either keyword provider for keyword option sets:

| Provider | Search coverage |
| --- | --- |
| **GND Keyword Synonym Provider** (`gnd_keyword_synonyms`) | Preferred names and synonyms stored in Lobid, including English aliases. |
| **GND SRU Keywords Provider** (`gnd_sru_keywords`) | DNB preferred names, synonyms, and multilingual vocabulary mappings. |

Both include the complete GND `SubjectHeading` family, including software products,
chemical and biological names, languages, and other subject-heading subtypes.
People, institutions, places, and works are excluded. The general **GND Provider**
(`gnd`) remains available for searches across all entity types.

The synonym provider searches only `preferredName` and `variantName`, using
`filter=type:SubjectHeading`. Input is quoted as a phrase in each field, with
quotes and backslashes escaped; no wildcard is appended. Each uncached search
makes one Lobid request and preserves its result ordering. English input works
when the term is present in one of these fields: for example, `fuel pellet` can
find **Brennstofftablette** (`7707637-0`). It does not search English labels from
linked vocabularies when Lobid exposes only their URIs. In particular, `fuel`
is not a synonym on the **Brennstoff** record; use the SRU provider for that match.
Display labels use the record's preferred name, rather than the matching synonym.

The SRU provider searches preferred names first (`dnb.an`), then adds matches
from the subject index (`dnb.sw`), including synonyms and multilingual mappings.
Both queries restrict results to subject headings (`dnb.bbg = Ts*`). For example,
English `fuel` can find **Brennstoff** (`4008186-2`), and `field work` can find
**Feldforschung** (`4016674-0`). English coverage depends on the mappings available
in DNB's index; it is not a translation service and does not reproduce GND
Explorer's ranking. Results use the canonical German preferred names and GND
identifiers from DNB's RDF records.

Each SRU search requests up to ten records from each index, then returns up to ten
distinct options, with preferred-name results first and upstream order preserved
within each group. Input is treated as literal search text; CQL operators,
wildcards, and anchors are escaped. No wildcard is appended automatically.
An uncached SRU search makes two requests to DNB; a direct identifier lookup makes
one. The online providers share the cache and request limits described below. If either
SRU search request fails, the provider returns no options and logs a warning.

Pasted GND identifiers and canonical GND URLs are subject to the same entity
restriction in both keyword providers, including when a record is already cached
by the general provider. Selecting either keyword provider for an existing option
set preserves saved answers and bare external identifiers; previously saved
people or institutions are not offered as new keyword selections. No frontend change,
local dataset import, or plugin database migration is required.


Display and mapped fields
-------------------------

GND identifier links open in a new tab by default. To configure the target of
links generated by the provider, set this in `config/settings/local.py`:

```python
GND_PROVIDER_LINK_TARGET = '_blank'  # default: request a new tab
```

Use `'_self'` to request the current tab, or `None` to omit the target attribute
and generate the previous link format. Links with a target also include
`rel="noopener noreferrer"`. Django escapes the preferred name, occupation text,
link URL, target, and identifier when generating the HTML. Saved display labels
are decoded back to their original search text; typed queries retain literal HTML
entities. The setting affects search results and direct identifier lookups in all
providers; it also applies when rendering cached responses.
Previously saved labels receive the new link format when RDMO refreshes them.

RDMO's frontend may enforce its own link targets. In particular, RDMO 2.5.2's
select widget sets selected links to `'_blank'` regardless of the provider HTML;
the current-tab setting only applies where the frontend preserves the target.


If a selection of a GND identifier should update other fields, you can add a `GND_PROVIDER_MAP` in your settings, e.g.:

```python
GND_PROVIDER_MAP = [
    {
        'gndIdentifier': 'https://rdmorganiser.github.io/terms/domain/project/coordination/gnd',
        'preferredName': 'https://rdmorganiser.github.io/terms/domain/project/coordination/name'
    }
]
```

In this case, a change to the identifier of a coordinator (`https://rdmorganiser.github.io/terms/domain/project/coordination/gnd`) will update their name (`https://rdmorganiser.github.io/terms/domain/project/coordination/name`) automatically. The value will be taken from the `preferredName` field of the response from the API for the selected `gndIdentifier`. `GND_PROVIDER_MAP` is a list of mappings, since multiple GND identifiers could be used and should update different other values.

Additional parameters can be provided using `GND_PARAMS`:

```python
GND_PARAMS = {
    'filter': '+(type:PlaceOrGeographicName)'
}
```

[lobid's policy](http://lobid.org/usage-policy/) asks to add a custom `User-Agent` to your requests so that they can perform statistical analyses and, if you add an email address, might contact you. This can be done by adding the following to your settings.

```python
GND_PROVIDER_HEADERS = {
    'User-Agent': 'Mein Projekt; mailto:meinprojekt@example.org'
}
```

Custom headers are merged with the default header case-insensitively. Setting
`GND_PROVIDER_HEADERS = None` is equivalent to an empty mapping and retains the
default `User-Agent`. Configuring other headers also preserves it; an explicitly
empty or `None` User-Agent is reported as a configuration error.

Header names and values may be text or bytes. Byte names are decoded as ASCII and
byte values as Latin-1, preserving their HTTP wire representation. The same
normalized headers are used for requests and cache keys, so equivalent byte and
text headers share cache entries. Invalid header names, values, and encodings are
reported as configuration errors. A `None` value for another header retains
Requests' behaviour of removing that header from its session defaults.

The SRU provider sends the same configured `User-Agent` to DNB. Other entries
in `GND_PROVIDER_HEADERS` are used only for Lobid requests, so endpoint-specific
headers are not forwarded to the additional service.


Search limits and request handling
----------------------------------

All providers support the following settings in `config/settings/local.py`:

| Setting | Default | Meaning |
| --- | --- | --- |
| `GND_SEARCH_MIN_LEN` | `1` | Minimum number of characters in a keyword search, after removing saved display-label decorations and surrounding whitespace. Must be a positive integer. |
| `GND_CACHE_CONFIG` | `None` | Optional dictionary with `alias` and `timeout` keys. A non-empty dictionary enables caching; missing, `None`, `{}`, or a zero timeout disables it. See below. |
| `GND_REQUEST_TIMEOUT` | `(3, 10)` | Connect and read timeouts in seconds. Accepts a positive number or a pair of positive numbers. The read timeout limits the wait between received bytes, rather than the total request duration. |

For keyword fields, consider setting `GND_SEARCH_MIN_LEN = 3` to avoid requests for
single letters and other very short input. This also excludes short abbreviations.
Bare GND identifiers (such as `2129905-5` or `11850391X`) and canonical
`https://d-nb.info/gnd/...` URLs use direct record lookups, independently of the
keyword length setting. The default minimum of one character preserves existing
keyword search behaviour. These settings do not change RDMO's frontend debounce.

The general provider, synonym provider, and `GND_PROVIDER_MAP` handler use
`GND_PROVIDER_URL` (default `https://lobid.org/gnd`) and `GND_PROVIDER_HEADERS`. The
SRU provider uses `https://services.dnb.de/sru/authorities` with SRU 1.1 and `RDFxml`
records. All clients share request and cache handling. Responses are checked for HTTP
errors, invalid JSON or XML, SRU diagnostics, and the fields required by the
provider before they are cached or used. Keyword responses must contain an
allowed subject-heading type as well as a consistent GND identifier and name.

On an upstream failure, autocomplete returns an empty list and mapped fields are
left untouched. The existing RDMO UI therefore cannot distinguish an outage from
an empty search. The `rdmo_gnd.client` logger records warnings with the upstream
status and request ID when available, without logging response bodies or request
headers. Cache hits and misses are logged at DEBUG level. Invalid setting values
are reported by `python manage.py check` as `rdmo_gnd.E001` errors with setting
names and corrective hints. Independent errors are collected together; direct
client construction raises `ImproperlyConfigured` for the same invalid settings.
Configuration checks perform no HTTP requests or database queries.


Shared database cache
---------------------

Caching is disabled by default. To opt in, set a non-empty `GND_CACHE_CONFIG`
dictionary in `config/settings/local.py`. The plugin uses Django's cache framework
and needs no additional caching package or service. To use the installation's
`default` cache:

```python
GND_CACHE_CONFIG = {'alias': 'default'}
```

The supported keys are:

| Key | Default when enabled | Meaning |
| --- | --- | --- |
| `alias` | `'default'` | Cache alias defined in Django's `CACHES` setting. |
| `timeout` | `43200` | Cache lifetime in seconds (12 hours). Must be a non-negative integer. Set to `0` to disable caching. |

Missing configuration, `None`, and `{}` disable caching. No cache object is
constructed; clients fetch directly without cache lookups, key generation,
savepoints, or cache logging. A zero timeout uses the same direct path and does
not require the alias to exist. Malformed dictionaries, unknown keys, and invalid
alias or timeout values are configuration errors.

The previous `GND_CACHE_ALIAS` and `GND_CACHE_TIMEOUT` settings are no longer read.
Replace them with `GND_CACHE_CONFIG` to keep caching enabled. Existing cache tables
and entries remain usable; no database migration is needed.

Backend, table, and capacity settings remain in Django's `CACHES`. RDMO's usual
local-memory cache is per process; it does not share results between workers and
loses entries on restart.

To share responses across workers and tenants using the existing database, add a
dedicated cache alias without replacing other cache settings:

```python
CACHES['gnd'] = {
    'BACKEND': 'django.core.cache.backends.db.DatabaseCache',
    'LOCATION': 'rdmo_gnd_cache',
    'KEY_PREFIX': 'rdmo-gnd',
    'OPTIONS': {
        'MAX_ENTRIES': 5000,
        'CULL_FREQUENCY': 3,
    },
}

GND_SEARCH_MIN_LEN = 3
GND_CACHE_CONFIG = {
    'alias': 'gnd',
    'timeout': 12 * 60 * 60,
}
GND_REQUEST_TIMEOUT = (3, 10)
```

Before activating this configuration, inspect and create the cache table:

```bash
python manage.py createcachetable rdmo_gnd_cache --database default --dry-run
python manage.py createcachetable rdmo_gnd_cache --database default
python manage.py check
```

No plugin model or migration is required. Django manages a table with
`cache_key` (primary key), `value` (a pickled, Base64-encoded response dictionary),
and indexed `expires` columns. One entry holds an entire search response or an
individual GND record. Each SRU query is cached separately. Genuine zero-result
searches are cached; upstream errors are never cached as empty results. Entries
expire after the configured lifetime and can also be evicted as the cache fills.
`MAX_ENTRIES` is an approximate capacity target, not permanent storage. Django
handles expiration on access and capacity-based cleanup during writes; no scheduled
cleanup is required to start.

All tenants must use the same table, key prefix, and cache key configuration.
For deployments with database routers or tenant schemas, ensure that both cache
reads and writes resolve to a common table. The plugin does not configure database
routing itself. See [Django's database cache documentation](https://docs.djangoproject.com/en/5.2/topics/cache/#database-caching).

Cache keys hash the endpoint, request kind, query parameters, and configured
headers. They preserve query case and syntax and contain no site, user, or project
IDs. Identical requests can reuse entries across tenants; different endpoints or
headers produce separate entries. Header names and ordering are normalized, but
even different `User-Agent` values create separate entries. Only public Lobid and
DNB responses are cached; SRU entries have separate request namespaces
from Lobid entries. Mapped-field updates remain specific to each project.

Cache access failures are logged and successful upstream responses are still
returned. Incorrect aliases or backend configuration are configuration errors and
must be fixed. A missing table must be created before rollout. Setting
`GND_CACHE_CONFIG = None` disables caching without removing the table.

Database-cache reads and writes use nested savepoints on already-active Django
database connections. Recoverable cache SQL errors are rolled back before the
client falls back, preserving surrounding business writes. This also protects
routed read/write connections when a read removes expired entries. HTTP requests
run outside these savepoints; memory and file caches do not introduce database
transactions.

When enabled, all HTTP clients compose `GNDResponseCache` from `rdmo_gnd.cache`.
Otherwise, `response_cache` is `None` and `_get` calls `_fetch` directly. The cache's
`get_or_fetch` method coordinates backend access and calls a supplied fetch
function on a miss. The fetch function returns parsed, validated data, or `None`
on failure; a separate validator checks cached entries. Key generation and cache
savepoints are isolated in the same module. Clients pass their current effective
URL, parameters, and headers for every request, including SRU's filtered headers.
Custom client subclasses can override `cache_class`, or replace `response_cache`,
without changing request handling. Client cache events retain the
`rdmo_gnd.client` logger; a standalone cache component uses `rdmo_gnd.cache` by
default. Existing keys and entries remain compatible after updating the settings.

Concurrent identical cache misses may still make multiple upstream requests.
Previously unseen searches still depend on the selected provider's upstream
service; this cache does not provide a local GND search index, automatic retries,
or stale-result fallback.

Validate the configuration in staging using the production database engine:
confirm that a second worker/site reuses the first site's search, review cache
hit/miss logs and outgoing request volume, and monitor failures and database
overhead after rollout.


Development
-----------

Install the development dependencies in a virtual environment:

```bash
pip install -e '.[dev,local]'
pytest
ruff check rdmo_gnd tests
```

Tests follow RDMO's pytest conventions, using pytest-django for settings and
database isolation, pytest-mock's `mocker` fixture, plain assertions, and
parametrized cases. The pytest settings in `pyproject.toml` select `tests.settings`
by default. Unit tests run without database access; database-cache tests use
`django_db(transaction=True)` to verify real commits and rollbacks.

The suite uses isolated SQLite test databases and mocked Lobid and DNB SRU
responses. It includes actual database-cache entries, cross-site reuse, and SQL
failures inside transactions. The second database alias tests routing using
current model tables, avoiding historical RDMO data migrations that assume the default database. To run
part of the suite, use commands such as `pytest tests/test_client.py` or
`pytest -k cache`.

SRU tests include fixed English search examples, subject-type filtering, escaped
CQL input, preferred-name ordering, and service failures. An RDMO integration test
checks provider selection, the project options API, and saving and reloading GND
identifiers without changing existing answers. Synonym-provider tests cover
preferred-name and synonym queries, literal input, subject restrictions on search
and identifier lookups, and cache isolation from unrestricted searches.

For a manual staging check, register the providers, select `gnd_sru_keywords` for a
keyword option set, search for `fuel` and `field work`, save a selection, and reload
the project. Confirm that the selected identifier and label are retained, a pasted
person identifier is not offered, and option sets using `gnd` still allow people.
Then select `gnd_keyword_synonyms`, search for `fuel pellet`, and confirm that
**Brennstofftablette** is offered and that pasted person identifiers remain excluded.

To run the same suite against PostgreSQL, install its test driver and use a
dedicated test server and role with permission to create databases:

```bash
pip install 'psycopg[binary]'
PGHOST=localhost PGPORT=5432 PGUSER=gnd_tests PGDATABASE=rdmo_gnd_tests \
    pytest --ds=tests.settings_postgresql
```

The PostgreSQL test settings use the standard `PGHOST`, `PGPORT`, `PGUSER`,
`PGPASSWORD`, and `PGDATABASE` environment variables. Django creates and removes
`test_<PGDATABASE>` and `test_<PGDATABASE>_cache`; no production settings are
imported. PostgreSQL tests reproduce connection-aborting SQL errors that SQLite
does not reproduce, including failures during expired-entry cleanup.


Local keyword provider
----------------------

Install `rdmo-plugins-gnd[local]` and configure `GND_INDEX_PATH` to add
`GNDLocalKeywordsProvider` with key `gnd_local_keywords`. It searches preferred
names, variants, and multilingual equivalents locally, including English `fuel`
for **Brennstoff**. The three online providers remain available. The example XML
catalog includes a local keyword question and OptionSet.

[The local-index guide](docs/local-index.md) covers shared Ubuntu deployment,
bootstrap and systemd updates, offline attribute mapping with `lookup='local'`,
validation, rollback, settings, and CLI commands. Existing mappings default to
`lookup='lobid'`; `auto` opts in to local resolution when all requested fields are
supported. Local autocomplete always stays offline.

The package requires Python 3.12+. Hatchling and hatch-vcs derive built package
versions from Git tags; source checkouts use a placeholder until built. Release
builds need full Git history/tags. Do not edit the generated `_version.py`.


Additional general-provider search parameters
---------------------------------------------

`GND_PARAMS` adds parameters to the general lobid provider's search requests:

```python
GND_PARAMS = {'filter': '+(type:PlaceOrGeographicName)'}
```

Configured entries override default parameters, including `q` and `format`.
Use JSON output for compatible option results. The effective parameters are
included in cache keys. This setting does not affect identifier lookups or the
specialized keyword providers, which enforce their own subject-heading searches.


The CI suite also installs the built wheel with its local extra into a fresh
virtual environment outside the source checkout. It verifies package/version and
legal-file inclusion, then runs the standalone CLI's build, search, and status
commands without Django or RDMO installed. To run it locally after building:

```bash
python -m build
python tests/wheel_smoke.py dist
```
